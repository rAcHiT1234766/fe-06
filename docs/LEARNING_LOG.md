# Learning log

## Phase 0 — Foundation

- **The workspace.** A pnpm monorepo: the root holds the shared settings (strict TypeScript, one ESLint config, one Vitest config that runs every package), and `packages/sdk` holds the product. Later phases add `packages/mock-engine`, `apps/mock-api` and `apps/demo` next to it.
- **Types first.** `core/types.ts` defines the shapes everything else is built against: the `Query` a widget asks for, the `DashboardConfig` JSON, the theme, and the token claims. `tsconfig.base.json` turns on `noUncheckedIndexedAccess` (an array lookup might be `undefined`) and `exactOptionalPropertyTypes` (an optional field may be missing, but is not automatically allowed to be `undefined`).
- **What integrators see.** `src/index.ts` re-exports the types, and the build bundles every declaration into one `dist/index.d.ts`. That file is what an editor reads to show tooltips, which is why each exported type has a short JSDoc comment.
- **Two builds from one source.** `vite.config.ts` builds an ES module for npm and leaves React out, because the host app already has React and two copies break hooks ("Invalid hook call"). `vite.element.config.ts` builds `dashkit.js` as one self-running script with React bundled in, for pages that use a plain `<script>` tag. That build replaces `process.env.NODE_ENV`, because React's code reads it and browsers have no `process`.
- **The Shadow DOM spike.** The custom element attaches a shadow root, turns a CSS file imported as a string (`?inline`) into a stylesheet adopted by that root, and mounts a React root inside it. The host page's selectors cannot match anything inside the shadow root, so even `button { background: red !important }` leaves the dashboard's button alone. Inherited properties such as font and text colour still flow in from the element itself, which the real element will have to reset.
- **Cleanup starts here.** `connectedCallback` mounts React when the element enters the page, and `disconnectedCallback` unmounts it when it leaves. Removing and re-adding the element gives a fresh, working counter.
- **Type tests.** `types.test-d.ts` checks the contracts with `expectTypeOf`, and Vitest runs it through the TypeScript compiler. Changing `DeepPartial` back to recursing into arrays makes the palette test fail, so the test does protect the agreed behaviour.
- **Measuring size and CI.** `pnpm size` reports three gzipped numbers: the npm file on its own, the npm file as a host app would bundle it (minified, React excluded), and `dashkit.js`. CI runs install, lint, typecheck, test, build, Storybook build and size on every push.

## Phase 1 — Data and permissions

- **The data.** `pnpm data:fetch` downloads the World Bank country list and seven indicators, drops the aggregates ("World", "High income" and so on), and pivots everything into one row per country and year, with `null` where a value is missing. It keeps only years that every indicator covers for at least half the countries, which ends the data at 2024. Region and income-level names come from the API: the World Bank now puts Afghanistan and Pakistan in "Middle East, North Africa, Afghanistan & Pakistan", which a hardcoded list would have missed.
- **One query path.** A widget describes what it wants as a `Query`. The API's `parseQuery` checks every field, operator and aggregation against the whitelist in `schema.ts`, ignores keys it does not know, and returns a clean query with every default filled in. `executeQuery` then works in a fixed order: row scope, filters, grouping, aggregation (skipping missing values), sorting (missing values last) and the row limit.
- **Row-level security.** The user's regions come from their verified token and decide which rows exist for that request. Because this happens before the user's own filters, a filter asking for a forbidden region simply finds nothing: status 200 with zero rows, which also avoids revealing that such rows exist.
- **Tokens.** A demo token is a JWT signed with HS256 that lasts 15 minutes and carries `tenantId`, `role` and `scopes`. The API checks the signature and expiry before it looks at the route, and reads tenant and role only from the verified token. Dashboards are stored under `tenant/id`, so another tenant's dashboard is simply "not found" (404), not "forbidden".
- **One API, two hosts.** `createApi` turns a web-standard `Request` into a `Response`. The Node server in `apps/mock-api` converts Node's request into a `Request` and adds CORS headers; the MSW handlers pass intercepted browser or test requests to the very same function.
- **The QueryClient.** It is the only way the SDK talks to the API. It adds the token to every request; after a 401 it asks `getToken` once for a new token and retries once. It caches each result under a key built from the query with its object keys sorted, shares one request between identical queries in flight, and empties the cache whenever the token changes, so one user's results can never be shown to another.
- **How the tests prove it.** The engine is tested on five hand-made rows, where every expected number can be checked by eye. The API tests follow the security table in the guide (missing, tampered, forged, foreign-key and expired tokens, 403 for viewers, 404 across tenants). The permission matrix runs each demo user through eight fixed queries, including every query on the starter dashboard. Turning row-level security off makes 8 tests fail.
- **A TypeScript speed trap.** Importing a 1.6 MB JSON file makes TypeScript infer a type for all of it. A small declaration file next to it (`wdi.d.json.ts`) states the type instead and cut checking from 3.8 s to 0.06 s.

## Phase 2 — Widgets and theming

- **From brand to CSS.** A host passes a partial theme. `createTheme` fills every missing value from `defaults.ts`, `resolveTheme` picks the light or dark colours (following the operating system in `auto` mode), and `toCssVars` turns them into `--dk-*` variables. Components only ever write `var(--dk-color-primary)` and the like, so a brand restyles everything without touching a component, and a test fails if a colour, font or radius is written into one.
- **Where the styles live.** The CSS files are imported as strings, and `ThemeRoot` writes them into a `<style>` element together with one `:where(.dk-root[data-dk-theme="…"])` rule holding the variables. `:where()` has zero specificity, so a host's ordinary CSS can still override any variable. The same strings will later go into the Web Component's shadow root.
- **Charts follow the same theme.** ECharts draws on a canvas, which cannot read CSS variables. `buildEChartsTheme` builds an ECharts theme from the same resolved theme, and `useEChart` applies it with `setTheme` on the existing chart, so switching brand or mode recolours charts without recreating them or sending new queries.
- **Option builders are plain functions.** `buildBarOption`, `buildLineOption` and `buildPieOption` turn a query result and a widget config into an ECharts option. With no React inside, the tests check their output directly as data.
- **The ECharts hook.** `useEChart` registers only the bar, line and pie modules, so the rest of ECharts stays out of the bundle. It creates the chart once, resizes it with a `ResizeObserver` and again when web fonts finish loading, turns animation off for reduced motion, and disposes of the chart on unmount.
- **The provider and a new user.** `DashKitProvider` creates one query client per API URL and token. A new token means a new client with an empty cache, and `useWidgetData` ignores any result fetched by an earlier client, so one user's numbers can never appear for another. `getToken` is handed over in a layout effect, which runs before any widget's data effect.
- **A widget's life.** `WidgetFrame` asks `useWidgetData` for the widget's result and shows a skeleton while loading, "No data for this selection" for zero rows, an error with a plain title such as "Session invalid" on failure, and otherwise the view for the widget's type. Charts also render a visually hidden table, so screen readers get the same numbers.
- **Testing what users see.** Component tests render real widgets in happy-dom with Testing Library, against the same MSW mock API the browser uses. The FR-2.6 test reads source files from disk because Vitest gives CSS imports to tests as empty strings; adding `color: #ff0000` to `widget.css` makes it fail.

## Phase 3 — Cross-filtering

- **One store, many readers.** `createFilterStore` is a plain object with the active filters, `subscribe` and `getFilters`, so the core stays free of React. Components read it with `useSyncExternalStore`, which re-renders the ones that read it whenever the filters change and never lets two widgets see different filters in the same render.
- **From a click to a query.** ECharts reports which item was clicked by its index. The widget looks up that row's raw value and calls `toggle(field, value, widgetId)`: a new value replaces the old one, and the same value again removes the filter. Every widget then rebuilds its query: `filtersFor` picks the filters that apply to it (none of its own, none at all with `listen: false`), and `mergeQuery` appends them as `in` filters.
- **Permissions still come first.** The API removes the rows a user may not see before it applies any filter, so a filter can only narrow what the user could already see. A filter on a forbidden region simply returns no rows.
- **The source chart highlights instead of filtering itself.** The option builder gets the selected values, dims the other items to 35% opacity and outlines the selected one, so the chart keeps all its bars.
- **No blank flashes, no stale answers.** A widget keeps its last result on screen while the new one loads, with `aria-busy` and a thin bar along its top edge. If the query changes again before the answer arrives, the effect's cleanup aborts the wait, so the late answer is dropped. Removing a filter returns to a query that is already in the client's cache, so it is instant.
- **The keyboard path.** A chart's visually hidden data table turns its values into toggle buttons. When one has focus, `:focus-within` makes the table cover the chart, so sighted keyboard users see what they are pressing.
- **The host's side.** `onFilterChange` subscribes to the store, and a new `filters` array from the host replaces the store's contents. The provider creates the store with the host's filters, so the first queries are already filtered.
- **Testing timing.** An MSW handler that waits on a promise holds back chosen answers, so a test can look at the screen in between and check that an answer arriving late is ignored. Each such test was checked by breaking the code it guards (no abort, the source chart filtering itself) and watching it fail.
- **End to end.** `pnpm test:e2e` has Playwright start the mock API and the demo app, then click the bar chart's canvas in Chromium. The test reads what each widget shows from its data table instead of from pixels, and asks for reduced motion so bars are drawn at full length before the click.

## Phase 4 — Dashboard builder

- **A grid that reports when a gesture ends.** react-grid-layout (v2) positions every widget from a layout of `{ i, x, y, w, h }` items and moves them up to fill gaps. The builder passes the draft's layout in and listens for `onDragStop` and `onResizeStop`, so a drag across half the screen produces one change. Dragging starts only from the handle in the widget's header, so clicks on a chart still filter in the builder.
- **Loaded, draft and saved.** The loader provides the config from the API. The builder keeps a draft beside it, and after a save the stored copy too, each tagged with the config it started from. When that tag no longer matches what is loaded, as after switching user, the draft and the copy are ignored, so nothing from one user's session shows in another's.
- **One registry, three readers.** The palette lists the registry's types, the grid takes each type's minimum size, and the config panel shows the settings each type lists. A sixth widget type means one more entry.
- **Edits as pure functions.** Adding, removing and duplicating widgets, and every setting in the panel, are functions from one config to a new one in `core/config`. They are tested without React, and the builder only decides which one to call.
- **Fields from the API.** The panel's measures, groupings and aggregations come from `/meta`, so a user is offered only what the API will accept. If `/meta` fails, the panel still edits the title and type and says why the rest is missing.
- **Saving.** Save checks the draft, sends it with `PUT /dashboards/:id`, and shows the stored result. The API checks the role again, so a viewer's save fails even if the controls were somehow shown. `migrate()` runs on every config that is loaded or given, so a future schema change has one place to convert old dashboards.
- **Focus.** A control that disappears takes the focus with it, so the builder moves the focus on purpose: to the new widget's Configure button after adding it, to the title when the panel opens, back to the opener when it closes, and to Edit dashboard when the builder closes.
- **Testing drags.** Playwright's mouse works in viewport coordinates, so the end-to-end test scrolls each handle into view before dragging and records widget positions relative to the page. After a reload it compares every widget's title, position, size and data. Running it found that resize corners showed outside the builder.
