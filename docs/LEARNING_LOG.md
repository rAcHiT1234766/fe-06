# Learning log

## Phase 0 — Foundation

- **The workspace.** A pnpm monorepo: the root holds the shared settings (strict TypeScript, one ESLint config, one Vitest config that runs every package), and `packages/sdk` holds the product. Later phases add `packages/mock-engine`, `apps/mock-api` and `apps/demo` next to it.
- **Types first.** `core/types.ts` defines the shapes everything else is built against: the `Query` a widget asks for, the `DashboardConfig` JSON, the theme, and the token claims. `tsconfig.base.json` turns on `noUncheckedIndexedAccess` (an array lookup might be `undefined`) and `exactOptionalPropertyTypes` (an optional field may be missing, but is not automatically allowed to be `undefined`).
- **What integrators see.** `src/index.ts` re-exports the types, and the build bundles every declaration into one `dist/index.d.ts`. That file is what an editor reads to show tooltips, which is why each exported type has a short JSDoc comment.
- **Two builds from one source.** `vite.config.ts` builds an ES module for npm and leaves React out, because the host app already has React and two copies break hooks ("Invalid hook call"). `vite.element.config.ts` builds `dashkit.js` as one self-running script with React bundled in, for pages that use a plain `<script>` tag. That build replaces `process.env.NODE_ENV`, because React's code reads it and browsers have no `process`.
- **The Shadow DOM spike.** The custom element attaches a shadow root, turns a CSS file imported as a string (`?inline`) into a stylesheet adopted by that root, and mounts a React root inside it. The host page's selectors cannot match anything inside the shadow root, so even `button { background: red !important }` leaves the dashboard's button alone. Inherited properties such as font and text colour still flow in from the element itself, which the real element will have to reset.
- **Cleanup starts here.** `connectedCallback` mounts React when the element enters the page, and `disconnectedCallback` unmounts it when it leaves. Removing and re-adding the element gives a fresh, working counter.
- **Type tests.** `types.test-d.ts` checks the contracts with `expectTypeOf`, and Vitest runs it through the TypeScript compiler. Changing `DeepPartial` back to recursing into arrays makes the palette test fail, so the test does protect the agreed behaviour.
- **Measuring size and CI.** `pnpm size` reports three gzipped numbers: the npm file on its own, the npm file as a host app would bundle it (minified, React excluded), and `dashkit.js`. CI runs install, lint, typecheck, test, build, Storybook build and size on every push.

## Phase 1 — Data and permissions

- **The data.** `pnpm data:fetch` downloads the World Bank country list and seven indicators, drops the aggregates ("World", "High income" and so on), and pivots everything into one row per country and year, with `null` where a value is missing. It keeps only years that every indicator covers for at least half the countries, which ends the data at 2024. Region and income-level names come from the API: the World Bank now puts Afghanistan and Pakistan in "Middle East, North Africa, Afghanistan & Pakistan", which a hardcoded list would have missed.
- **One query path.** A widget describes what it wants as a `Query`. The API's `parseQuery` checks every field, operator and aggregation against the whitelist in `schema.ts`, ignores keys it does not know, and returns a clean query with every default filled in. `executeQuery` then works in a fixed order: row scope, filters, grouping, aggregation (skipping missing values), sorting (missing values last) and the row limit.
- **Row-level security.** The user's regions come from their verified token and decide which rows exist for that request. Because this happens before the user's own filters, a filter asking for a forbidden region simply finds nothing: status 200 with zero rows, which also avoids revealing that such rows exist.
- **Tokens.** A demo token is a JWT signed with HS256 that lasts 15 minutes and carries `tenantId`, `role` and `scopes`. The API checks the signature and expiry before it looks at the route, and reads tenant and role only from the verified token. Dashboards are stored under `tenant/id`, so another tenant's dashboard is simply "not found" (404), not "forbidden".
- **One API, two hosts.** `createApi` turns a web-standard `Request` into a `Response`. The Node server in `apps/mock-api` converts Node's request into a `Request` and adds CORS headers; the MSW handlers pass intercepted browser or test requests to the very same function.
- **The QueryClient.** It is the only way the SDK talks to the API. It adds the token to every request; after a 401 it asks `getToken` once for a new token and retries once. It caches each result under a key built from the query with its object keys sorted, shares one request between identical queries in flight, and empties the cache whenever the token changes, so one user's results can never be shown to another.
- **How the tests prove it.** The engine is tested on five hand-made rows, where every expected number can be checked by eye. The API tests follow the security table in the guide (missing, tampered, forged, foreign-key and expired tokens, 403 for viewers, 404 across tenants). The permission matrix runs each demo user through eight fixed queries, including every query on the starter dashboard. Turning row-level security off makes 8 tests fail.
- **A TypeScript speed trap.** Importing a 1.6 MB JSON file makes TypeScript infer a type for all of it. A small declaration file next to it (`wdi.d.json.ts`) states the type instead and cut checking from 3.8 s to 0.06 s.

## Phase 2 — Widgets and theming

- **From brand to CSS.** A host passes a partial theme. `createTheme` fills every missing value from `defaults.ts`, `resolveTheme` picks the light or dark colours (following the operating system in `auto` mode), and `toCssVars` turns them into `--dk-*` variables. Components only ever write `var(--dk-color-primary)` and the like, so a brand restyles everything without touching a component, and a test fails if a colour, font or radius is written into one.
- **Where the styles live.** The CSS files are imported as strings, and `ThemeRoot` writes them into a `<style>` element together with one `:where(.dk-root[data-dk-theme="…"])` rule holding the variables. `:where()` has zero specificity, so a host's ordinary CSS can still override any variable. The same strings will later go into the Web Component's shadow root.
- **Charts follow the same theme.** ECharts draws on a canvas, which cannot read CSS variables. `buildEChartsTheme` builds an ECharts theme from the same resolved theme, and `useEChart` applies it with `setTheme` on the existing chart, so switching brand or mode recolours charts without recreating them or sending new queries.
- **Option builders are plain functions.** `buildBarOption`, `buildLineOption` and `buildPieOption` turn a query result and a widget config into an ECharts option. With no React inside, the tests check their output directly as data.
- **The ECharts hook.** `useEChart` registers only the bar, line and pie modules, so the rest of ECharts stays out of the bundle. It creates the chart once, resizes it with a `ResizeObserver` and again when web fonts finish loading, turns animation off for reduced motion, and disposes of the chart on unmount.
- **The provider and a new user.** `DashKitProvider` creates one query client per API URL and token. A new token means a new client with an empty cache, and `useWidgetData` ignores any result fetched by an earlier client, so one user's numbers can never appear for another. `getToken` is handed over in a layout effect, which runs before any widget's data effect.
- **A widget's life.** `WidgetFrame` asks `useWidgetData` for the widget's result and shows a skeleton while loading, "No data for this selection" for zero rows, an error with a plain title such as "Session invalid" on failure, and otherwise the view for the widget's type. Charts also render a visually hidden table, so screen readers get the same numbers.
- **Testing what users see.** Component tests render real widgets in happy-dom with Testing Library, against the same MSW mock API the browser uses. The FR-2.6 test reads source files from disk because Vitest gives CSS imports to tests as empty strings; adding `color: #ff0000` to `widget.css` makes it fail.

## Phase 3 — Cross-filtering

- **One store, many readers.** `createFilterStore` is a plain object with the active filters, `subscribe` and `getFilters`, so the core stays free of React. Components read it with `useSyncExternalStore`, which re-renders the ones that read it whenever the filters change and never lets two widgets see different filters in the same render.
- **From a click to a query.** ECharts reports which item was clicked by its index. The widget looks up that row's raw value and calls `toggle(field, value, widgetId)`: a new value replaces the old one, and the same value again removes the filter. Every widget then rebuilds its query: `filtersFor` picks the filters that apply to it (none of its own, none at all with `listen: false`), and `mergeQuery` appends them as `in` filters.
- **Permissions still come first.** The API removes the rows a user may not see before it applies any filter, so a filter can only narrow what the user could already see. A filter on a forbidden region simply returns no rows.
- **The source chart highlights instead of filtering itself.** The option builder gets the selected values, dims the other items to 35% opacity and outlines the selected one, so the chart keeps all its bars.
- **No blank flashes, no stale answers.** A widget keeps its last result on screen while the new one loads, with `aria-busy` and a thin bar along its top edge. If the query changes again before the answer arrives, the effect's cleanup aborts the wait, so the late answer is dropped. Removing a filter returns to a query that is already in the client's cache, so it is instant.
- **The keyboard path.** A chart's visually hidden data table turns its values into toggle buttons. When one has focus, `:focus-within` makes the table cover the chart, so sighted keyboard users see what they are pressing.
- **The host's side.** `onFilterChange` subscribes to the store, and a new `filters` array from the host replaces the store's contents. The provider creates the store with the host's filters, so the first queries are already filtered.
- **Testing timing.** An MSW handler that waits on a promise holds back chosen answers, so a test can look at the screen in between and check that an answer arriving late is ignored. Each such test was checked by breaking the code it guards (no abort, the source chart filtering itself) and watching it fail.
- **End to end.** `pnpm test:e2e` has Playwright start the mock API and the demo app, then click the bar chart's canvas in Chromium. The test reads what each widget shows from its data table instead of from pixels, and asks for reduced motion so bars are drawn at full length before the click.

## Phase 4 — Dashboard builder

- **A grid that reports when a gesture ends.** react-grid-layout (v2) positions every widget from a layout of `{ i, x, y, w, h }` items and moves them up to fill gaps. The builder passes the draft's layout in and listens for `onDragStop` and `onResizeStop`, so a drag across half the screen produces one change. Dragging starts only from the handle in the widget's header, so clicks on a chart still filter in the builder.
- **Loaded, draft and saved.** The loader provides the config from the API. The builder keeps a draft beside it, and after a save the stored copy too, each tagged with the config it started from. When that tag no longer matches what is loaded, as after switching user, the draft and the copy are ignored, so nothing from one user's session shows in another's.
- **One registry, three readers.** The palette lists the registry's types, the grid takes each type's minimum size, and the config panel shows the settings each type lists. A sixth widget type means one more entry.
- **Edits as pure functions.** Adding, removing and duplicating widgets, and every setting in the panel, are functions from one config to a new one in `core/config`. They are tested without React, and the builder only decides which one to call.
- **Fields from the API.** The panel's measures, groupings and aggregations come from `/meta`, so a user is offered only what the API will accept. If `/meta` fails, the panel still edits the title and type and says why the rest is missing.
- **Saving.** Save checks the draft, sends it with `PUT /dashboards/:id`, and shows the stored result. The API checks the role again, so a viewer's save fails even if the controls were somehow shown. `migrate()` runs on every config that is loaded or given, so a future schema change has one place to convert old dashboards.
- **Focus.** A control that disappears takes the focus with it, so the builder moves the focus on purpose: to the new widget's Configure button after adding it, to the title when the panel opens, back to the opener when it closes, and to Edit dashboard when the builder closes.
- **Testing drags.** Playwright's mouse works in viewport coordinates, so the end-to-end test scrolls each handle into view before dragging and records widget positions relative to the page. After a reload it compares every widget's title, position, size and data. Running it found that resize corners showed outside the builder.

## Phase 5 — Embedding and responsive

- **A custom element's lifecycle.** The browser calls `connectedCallback` when the element enters the page, `disconnectedCallback` when it leaves, and `attributeChangedCallback` for each name in `observedAttributes`. `<dashkit-dashboard>` creates its shadow root and React root on connect, renders again on every attribute or property change, and unmounts the React root when it is removed, which disposes the charts and disconnects their observers.
- **Properties set too early.** A page may set `el.theme` before the script that defines the element has run. That creates a plain property on the element which hides the class's setter, so on connect the element reads such properties, deletes them and sets them again through the setter (the "upgrade property" pattern).
- **Events across the shadow boundary.** Events from inside a shadow root stop at its edge unless they are `composed`. The element dispatches `dashkit:*` events on itself with `bubbles` and `composed`, so a listener on the element or on `document` hears them.
- **Isolation in both directions.** The host's selectors cannot match anything in the shadow root, and the dashboard's styles live inside it, so neither side can restyle the other. Inherited properties are the exception: they flow in from the element itself, which is why the dashboard root starts from `all: initial`.
- **Waiting for what is needed.** Pages set `getToken` in a script after the one that defines the element, so the element renders nothing until it has an API URL, a dashboard and a way to get a token.
- **`DashKit.mount()`.** The script build is an IIFE named `DashKit`, so the entry's exports become properties of `window.DashKit`. `mount()` creates a `<dashkit-dashboard>`, maps the options onto attributes and properties, and turns the element's events back into the option callbacks.
- **Container breakpoints.** The dashboard measures its own root with a `ResizeObserver`, so the same dashboard is one column in a sidebar and twelve on a wide page. The breakpoint goes into a context; the grid reads it to choose a layout and a column count, and the builder reads it to decide whether editing fits.
- **Deriving a layout.** Only the twelve-column layout is stored. `deriveLayout` scales each widget's edges into fewer columns, keeps a minimum width, places widgets in reading order and widens the last one in each row, so rows end flush. It is a pure function, tested on the demo's own layout.
- **Touch.** `@media (any-pointer: coarse)` matches when a finger is available, and there every control is at least 44 px square. ECharts turns taps into the same click events, so tapping a bar filters as clicking does.
- **Testing in a test DOM that does no layout.** happy-dom supports custom elements and shadow roots but reports a width of zero, so the responsive tests replace `getBoundingClientRect` and `ResizeObserver` and resize a pretend container by hand.
- **Testing "looks unchanged".** The end-to-end test screenshots the element until two shots match, adds hostile styles to the page, and compares the next shot pixel by pixel in the browser, allowing only anti-aliasing noise.
- **Testing installability.** `pnpm pack` builds the tarball an npm install would get. Installed into an empty project outside the workspace, it typechecks a small host app under strict settings with `skipLibCheck` off, and `@ts-expect-error` lines prove that wrong usage is rejected.

## Phase 6 — Quality and documentation

- **One test suite, two React versions.** A Vitest project can point at another package's test files. `packages/react18-check` does that for the SDK's component tests and resolves `react` and `react-dom` (and paths below them, such as `react-dom/client`) to React 18 copies installed beside it, so the SDK's source runs against React 18 without changing a line.
- **Global type augmentation.** `declare global { interface HTMLElementTagNameMap { ... } }` merges a new tag into the DOM's own types, so `querySelector('dashkit-dashboard')` returns the element's class. `declare module 'react' { namespace JSX { ... } }` does the same for JSX. Such declarations apply to every file in a program that sees them, which is why they live in a file of their own that hosts opt into by importing the element entry.
- **Typed event listeners.** Overloading `addEventListener` with `K extends keyof DashKitElementEventMap` lets TypeScript look up each event's type from its name, so `event.detail` is typed without a cast; any other event name falls through to a general overload that takes a string.
- **Testing a package as it ships.** `pnpm pack` produces the exact tarball npm would publish. Installing it into a fresh project outside the workspace, with `skipLibCheck` off, catches what workspace tests cannot: missing files, `.d.ts` files that only resolve inside the monorepo, and types that need options the host does not use.
- **User Timing.** `performance.mark(name)` records a moment and `performance.measure(name, start)` the time since a mark; both appear in the browser's performance panel and to any `PerformanceObserver`. The SDK marks mount and filter changes, and measures to ECharts' `finished` event, which fires once a chart has drawn and its animation has ended.
- **Why animation length is part of latency.** ECharts' `finished` waits for animations, and a series' default animation settings override the chart's, so the pie's 500 ms update and the line's one-second entrance set the cross-filter time until each series got a 200 ms duration of its own.
- **Measuring frames.** During a scripted drag, a `requestAnimationFrame` loop records the gap between frames. At 60 Hz a smooth gap is 16.7 ms; the 95th percentile and the count of gaps over 50 ms show stutter that an average would hide. Chrome's DevTools protocol can slow the CPU four times to approximate a slower device.
- **Docs that cannot drift.** The TypeScript compiler API can list a module's exports, their declarations and their JSDoc. Generating the API reference from it, and failing when a comment is missing, keeps the reference, the editor tooltips and the code in step.
- **Storybook's moving parts.** Globals are toolbar values shared by every story; loaders run before a story renders, again whenever its args or globals change, and put their results in `loaded`; decorators wrap stories, here in a `DashKitProvider` built from the globals and the loaded token. A story's own `globals` pin a value and disable that control. MDX docs pages attach to a stories file with `<Meta of={...}>` and embed its stories with `<Canvas>` and `<Controls>`.
- **Two builds, one output folder.** Vite empties `build.outDir` before it writes, which is right for a single build and wrong for two that share a folder: the second must set `emptyOutDir: false`, and in watch mode, where both rebuild on every change, neither may empty it. Plugins can delete files too. The type plugin writes a `.d.ts` per source file, bundles the ones the entry reaches, and deletes the rest, so a source file whose name matches another build's output takes that output with it.
- **Passive and layout effects.** React runs `useLayoutEffect` during the update itself, after the DOM changes but before the browser paints or any other code runs; `useEffect` runs a little later. Moving the focus belongs in a layout effect: when the focused button is removed, the browser puts the focus on the page body, and a passive effect leaves it there for a moment that screen readers and tests can notice.

## Phase 7 — Ship

- **Infrastructure as a file.** A Render Blueprint (`render.yaml`) lists services with their runtime, build and start commands and environment variables. Committing it means the deployment is reviewed and versioned like the code, and recreating the services is one action rather than a list of settings to copy.
- **Static sites and web services.** A static site is files a CDN serves; nothing runs after the build, so any setting it needs is baked in at build time. A web service runs a process that must listen on the port the host gives it in `PORT`, on every network interface, and the host checks a health path before sending it traffic.
- **Build-time environment variables in Vite.** Only variables prefixed `VITE_` reach the browser code, through `import.meta.env`, and Vite replaces `%VITE_NAME%` in HTML files the same way. The value is written into the built files, so it is public: an address is fine, a secret never is.
- **Secrets the host generates.** A secret that only one service uses, such as the key that signs and checks tokens, can be generated by the platform and never shown to anyone. The fewer people and files that ever hold a secret, the fewer places it can leak from.
- **CORS between separate origins.** The demo and the API have different addresses, so before a request that carries a token the browser sends a preflight request asking the API whether the demo's origin may call it. The API compares the request's `Origin` header with its allow list exactly and, on a match, names that origin in its answer. A browser's `Origin` is a scheme, host and port with no trailing slash, so a list entry with a slash or the wrong scheme never matches.
- **Free hosting sleeps.** A free service stops after a while without requests, and the next request waits while it starts again. A demo plan therefore starts with opening the health check, and the app's error message says to wait and reload rather than blaming the visitor's setup.
- **A demo script as a test.** Writing what each step must show turns a rehearsal into a check. Running the script, the console snippet included, against production builds before recording it found issues the unit tests could not, such as a development address left in a page.
- **Tracing requirements to tests.** Naming the requirement in each test's title makes coverage searchable. A search for every must-have ID showed which ones were only covered by accident or not at all, and a test that compares the element's markup with the React component's turns "built from the same source" from a claim into a check.

## After Phase 7 — Finishing the public options

- **What coverage measures.** V8 counts which statements, functions and branches ran while the tests ran. Branches score lowest because each `if`, `?:`, `??` and `&&` counts both ways, and the way not taken is often an error path. Coverage shows what no test reaches; it cannot show that a test checks the right thing.
- **A gate, not a goal.** Thresholds set at the level first measured stop a quiet decline, and per-folder thresholds let the logic be held to a high bar while interface code is judged by what its tests check.
- **Re-flowing a grid.** Scaling twelve columns to four rounds each share, and minimum widths can push a row over the edge. Taking one column at a time from the widest widget until the row fits keeps the proportions as close as the grid allows.
- **Client-side paging.** When a query already caps its rows, slicing them in the browser makes a page change instant and needs nothing from the API; a server would need an offset, a total and a request per page.
- **Deriving state instead of syncing it.** Storing the page together with the result it was chosen for, and treating any other result as page one, gives the right page in the same render. Resetting it in an effect would show the wrong page for a frame and render twice.
- **`aria-disabled` and focus.** A `disabled` button leaves the tab order and drops the focus if it has it; `aria-disabled` tells assistive technology the button does nothing while keeping it focusable.
- **Colour as text.** A colour used for words must reach 4.5:1 against what is behind it, like any text, and a status needs words or an icon besides its colour for readers who cannot tell the colours apart.
- **Proving a test can fail.** Reverting the change and running the new test again shows it would catch the bug; a test that passes either way protects nothing.
- **Container-measured layouts depend on the host.** A dashboard that picks its layout from its own width changes layout when the page around it changes, not only the window. A sidebar is a design choice with a cost in columns, so the end-to-end tests measure the dashboard at the screen sizes the demo is shown at.
- **One element, two places.** Grid items may share a cell: the navigation sits in the top bar's row, between the brand and the user, on medium screens and moves to a column of its own on wide ones, with no second copy for assistive technology to meet.
- **Browser state as an external store.** The address and the system colour scheme belong to the browser; `useSyncExternalStore` reads them during render and re-renders on `hashchange` or a media-query change, with no effect copying them into state.
- **Focus after client-side navigation.** A single-page app does not reload, so nothing tells a screen reader the page changed. Moving the focus to the new heading, made focusable with `tabIndex={-1}`, does.
- **Undo as a list of snapshots.** With immutable state, undo needs no inverse for each kind of edit: keep the versions before the current one and the ones after it, move between them, and forget the ones after on a new edit. Merging a run of edits to one field into one step is what makes it feel right while typing, and a text field's own Ctrl+Z belongs to the browser.
- **A keyboard alternative to dragging.** Using the grid library's own move and compaction for each key press keeps the keyboard and the pointer in step. Vertical compaction makes "one row down" mean little on its own, so a key press is better defined by its effect: the widget moved that way, or the user is told it cannot.
- **Test DOMs do not model focus loss.** jsdom and happy-dom kept the focus on an element React moved within the page, so only a run in real browsers could show whether code to restore it was needed. It was not, and the code went.
- **Modifier keys differ between platforms and between pointer and keyboard.** Ctrl-click is a right-click on a Mac, so multi-select takes Ctrl or Cmd. A click made with the keyboard does not reliably carry the modifier keys, or happen at all, so the key itself has to be handled; only the end-to-end run in three browsers showed this.
- **Column-level security.** Restricting columns is harder than restricting rows: rows can be removed before a query runs, but a column can leak through anything that uses it, so a filter on a forbidden measure has to be refused as well as showing it. Hiding fields in the interface only helps honest users; the server's check is the protection, and a test sends the forbidden query by hand to prove it.

## After Phase 7 — Beyond the requirements

- **CSV is simple until a spreadsheet opens it.** RFC 4180 quoting covers commas, quotes and line breaks, but a cell starting with `=`, `+`, `-` or `@` is run as a formula, so exported text needs a guard, and Excel reads a file without a byte order mark in the system's code page rather than UTF-8.
- **Exporting what is on screen needs no new request.** The widget already holds its filtered, scoped result, so a download from it can never hold more than the user may see, and the server's checks stay the only protection.
- **Downloads from a shadow root.** A temporary link with a `download` attribute works when it is placed inside the shadow root, and stays out of reach of a host's handler for link clicks there.
- **Boolean attributes across React versions.** React 19 adds or removes a custom element's boolean attribute, while React 18 writes `false` as the text "false"; an element that reads only whether the attribute is present would take that as true.
- **Test DOMs differ in small ways too.** happy-dom's `Blob.text()` keeps a byte order mark that browsers drop, so the test strips it itself rather than depending on either.
- **New features from existing state.** Drill-down needed no state of its own: a widget's own cross-filter selection already says which value was clicked, so drilling is a different query for that widget, and undo, the host's events and the chips work unchanged.
- **Focus and content that loads later.** When a click replaces content only after a request, the element that was clicked should stay until the new content arrives; deciding where the focus goes at the moment of the click, and moving it once the content is drawn, keeps keyboard users in place. A click made with Enter or Space has a `detail` of 0, which tells it from a pointer's.
- **Combining filters is a product decision.** Two filters on the same field can mean "both" or "this one instead". Cross-filter clicks narrow, which suits subsets such as regions; a dashboard-wide year is a parameter, which a selection should replace. Screenshots of a Year list that emptied every widget made the difference plain before any test did.
- **State that crosses components.** The picker and the builder are siblings that know nothing of each other, but a switch must not lose the builder's draft. A tiny registry on the shared provider, which the builder holds while it has unsaved changes, was enough, and kept both components independent.
- **Full-page screenshots can mislead.** A full-page capture of a phone-width page showed empty widget frames; measuring the widgets' boxes and taking a normal screenshot showed the charts were drawn. Checking with a second method before "fixing" a layout saved a change that was not needed.
- **Join datasets by code, not by name.** Natural Earth and the World Bank spell many countries differently, but both carry ISO 3166 codes. Even codes have exceptions: Natural Earth leaves `ISO_A3` at "-99" for France and Norway, whose other code fields are filled in, and gives Kosovo a code the World Bank does not use.
- **A sequential scale needs room at both ends.** Fading one colour towards the surface makes the pale classes distinct but bunches the top ones together. Continuing past the colour, towards the text, spreads them, and measuring each class's lightness showed the steps instead of leaving it to the eye.
- **Floating point reaches past 1.** `0.2 + (0.8 * 0.75) / 0.75` is `1.0000000000000002`, and ECharts blends nothing past 1, so the class meant to be the chart colour itself had no colour. The script that measured lightness failed on it before any screenshot showed it.
- **Charting defaults are not always what a map wants.** ECharts stretches a map to the box it is given unless `preserveAspect` is set, and in a pie or a map it passes `NaN` for a missing value, which the tooltip would otherwise print as "NaN".
- **A performance test measures the page around it too.** The filter lists and the picker put the grid 96 pixels lower, so the resize test's drag now passed within 20 pixels of the window's edge, where Chrome scrolls the page while a button is held, as it does for a text selection. The widget grew with the scroll and the test reported a slowdown the dashboard did not have. Bisecting the commits, then removing one piece at a time, then logging the page's geometry during the drag found it; starting every drag at the same height in the window fixed the measurement.
