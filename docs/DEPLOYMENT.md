# Deploying to Render

Three services go to [Render](https://render.com), all on its free plan, from one file in the
repository, [`render.yaml`](../render.yaml):

| Service             | Render type | What it serves                                                   | Built with                                                |
| ------------------- | ----------- | ---------------------------------------------------------------- | --------------------------------------------------------- |
| `dashkit-api`       | Web service | The demo data API, started with `node apps/mock-api/src/main.ts` | `pnpm install`; Node 24 runs the TypeScript directly      |
| `dashkit-demo`      | Static site | The demo app, the plain HTML page and `dashkit.js`               | The SDK build, then the demo build, from `apps/demo/dist` |
| `dashkit-storybook` | Static site | Storybook, with its data API running in the browser              | `build-storybook`, from `packages/sdk/storybook-static`   |

Storybook needs no server, so the API only ever talks to the demo app.

## Before you start

1. **Put the repository on GitHub.** Create an empty repository on GitHub, with no README, licence
   or `.gitignore`, so it accepts this history as it is. Then, in the project folder:

   ```sh
   git remote add origin https://github.com/<your-account>/<repository>.git
   git push -u origin master
   ```

2. **Create a Render account** at https://render.com, signing up with GitHub. When Render asks
   which repositories it may read, allow this one.

## Deploy

1. In the Render dashboard, choose **New**, then **Blueprint**.
2. Pick the repository. Render reads `render.yaml` and lists `dashkit-api`, `dashkit-demo` and
   `dashkit-storybook`. Name the Blueprint `dashkit`.
3. Render asks for two values. Each is the other service's address, which Render will give it
   from its name:

   | Variable                                     | Value                               |
   | -------------------------------------------- | ----------------------------------- |
   | `DASHKIT_ALLOWED_ORIGINS` (on `dashkit-api`) | `https://dashkit-demo.onrender.com` |
   | `VITE_DASHKIT_API_URL` (on `dashkit-demo`)   | `https://dashkit-api.onrender.com`  |

   Type them exactly: `https`, no trailing slash, no path.

4. Apply the Blueprint. Render builds all three; the first builds take a few minutes each. Wait
   until every service shows that it is live.
5. Open each service and note the address at the top of its page. If a name was already taken,
   Render adds a few characters to it, such as `dashkit-api-x7k2.onrender.com`. Then:
   - on `dashkit-api`, under **Environment**, set `DASHKIT_ALLOWED_ORIGINS` to the demo's real
     address and save;
   - on `dashkit-demo`, under **Environment**, set `VITE_DASHKIT_API_URL` to the API's real
     address and save. The demo reads it while building, so if Render does not start a new deploy
     by itself, choose **Manual Deploy**, then **Deploy latest commit**.

`DASHKIT_TOKEN_SECRET` needs nothing from you: Render generates it, and it stays on the API.

## Check that it works

1. Open `https://<api address>/health`. It shows `{"status":"ok"}`. The first visit can take up to
   a minute while the free service wakes up.
2. Open the demo's address. The "World development overview" dashboard appears. Switch to Ravi:
   the table shows only South Asia and East Asia & Pacific.
3. Open `https://<demo address>/plain-html/`. The same dashboard appears, from one script tag.
4. Open the Storybook address and pick any widget story.
5. Send me the three addresses. I will put them in the README, point the remaining docs at them,
   run the automated checks against them and record a Lighthouse score in `PERFORMANCE.md`.

## Settings

| Variable                  | Service        | Value                                                        | Notes                                                                                                                   |
| ------------------------- | -------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `DASHKIT_TOKEN_SECRET`    | `dashkit-api`  | Generated by Render                                          | Signs and checks embed tokens. Keep it secret. Changing it ends every open session; the SDK then fetches new tokens.    |
| `DASHKIT_ALLOWED_ORIGINS` | `dashkit-api`  | The demo's address, e.g. `https://dashkit-demo.onrender.com` | Browsers may call the API only from these origins. Separate several with commas. Each must match exactly.               |
| `PORT`                    | `dashkit-api`  | Set by Render                                                | The API listens on it.                                                                                                  |
| `VITE_DASHKIT_API_URL`    | `dashkit-demo` | The API's address, e.g. `https://dashkit-api.onrender.com`   | Built into the demo app and the plain HTML page. Public, like any address a browser calls. A change needs a new deploy. |
| `NODE_VERSION`            | all three      | `24`                                                         | Set in `render.yaml`. The API needs Node 24 to run TypeScript without a build step.                                     |

Every push to `master` deploys all three again.

## Before you present

- **Wake the API first.** A free web service sleeps after about 15 minutes without requests, and
  the first request after that takes up to a minute. Open `/health` a few minutes before you
  start, then load the demo.
- **Saved dashboards do not survive a restart.** The API keeps them in memory, so after it sleeps,
  restarts or redeploys, each customer is back to the starter dashboard. Do the builder part of
  the demo live, rather than preparing a dashboard in advance.
- Static sites do not sleep; only the API does.

## If something goes wrong

| What you see                                              | Likely cause and fix                                                                                                                                         |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The demo says "Could not reach the demo API at …"         | The API is still waking up: wait a minute and reload. If it persists, the address after "at" is wrong: fix `VITE_DASHKIT_API_URL` and deploy the demo again. |
| The browser console shows a CORS error                    | `DASHKIT_ALLOWED_ORIGINS` does not match the demo's address exactly. Check `https`, the spelling, and that there is no trailing slash.                       |
| A build fails at `npm install --global pnpm`              | Replace `npm install --global pnpm@12.21.0` with `corepack enable` in that service's build command; the repository pins the pnpm version in `package.json`.  |
| The API's deploy log shows a syntax error in a `.ts` file | Node is older than 24. Check that `NODE_VERSION` is `24` on `dashkit-api`.                                                                                   |
| The API log warns that `DASHKIT_TOKEN_SECRET` is not set  | The variable is missing. Add it with any long random value; until then tokens end whenever the API restarts.                                                 |

## Without a Blueprint

The same services can be created one by one with **New → Web Service** and **New → Static Site**,
using the build commands, start command, publish folders and variables in `render.yaml`.
